# Shorts analysis for creators

The goal is to help a creator inspect **what is visible and how it is composed** in a reference short video, while leaving the calling AI in control. This is an optional analysis layer, not an automatic video generator or a new detection/tracking model. It does not depend on OpenClaw.

## The independent operations

1. `extract SOURCE --out DIR [args]`: prepare individual frames, numbered contact sheet and manifest. Local FFmpeg/Pillow work only.
2. `analyze MANIFEST --out DIR`: prepare a schema, prompt and image list. No model call.
3. `analyze MANIFEST --backend import --response FILE --out DIR`: validate an AI's raw JSON response and write `analysis.json` + `report.md`. Offline.
4. `analyze MANIFEST --backend codex --out DIR`: explicitly send the selected images to your authenticated Codex service and validate its response. Optional convenience backend, not required by the data format.

Each invocation requires a fresh/empty output directory. JSON is written to stdout; failures exit nonzero. Analysis does not automatically download media, call follow-up commands or modify your video.

## Practical workflow

Assuming installation from the root README:

```sh
# Cheap overview to locate the interesting intervals
.venv/bin/python cli.py extract reference.mp4 --out output/overview \
  --max-frames 6 --width 240

# For fine text/layout detail, spend pixels on a smaller selected interval
.venv/bin/python cli.py extract reference.mp4 --out output/detail \
  --start 7.5 --end 10.5 --sampler uniform --max-frames 8 \
  --width 480 --columns 4 --no-endpoint

# Agent uses its own preferred image model
.venv/bin/python cli.py analyze output/detail/manifest.json --out output/request
```

Read `output/request/request.json`. Send its **individual image files as image inputs**, along with `prompt.txt` and `schema.json`, to your selected model. Do not just send filenames as text. Save the model's raw schema-matching JSON (not Markdown fences, not the final `analysis.json` wrapper):

```sh
.venv/bin/python cli.py analyze output/detail/manifest.json --out output/result \
  --backend import --response model-response.json
```

Alternatively:

```sh
.venv/bin/python cli.py analyze output/detail/manifest.json --out output/codex-result \
  --backend codex --model gpt-5.6-luna --effort low --timeout 180 --language Korean
```

The optional backend requires POSIX process groups and an installed, authenticated Codex CLI with `--image`, `--output-schema`, `--json`, `--ephemeral`, `--ignore-user-config`, and `--sandbox read-only`. It preserves authentication but does not load the user's normal config for this invocation. Custom provider/config workflows should use prepare/import. Select a model that accepts image inputs and the reasoning effort you request; support and service cost depend on your account. No API keys belong in this repository.

## Analysis options

- Positional `manifest`: manifest generated by the extraction command. Image paths must remain within its directory, including through symlinks. Keep the manifest with its frames.
- `--out DIR`: required fresh/empty output directory.
- `--backend prepare|import|codex`: default `prepare` is offline.
- `--response FILE`: required only for `import`; raw JSON from any model or a completed `response.raw.json` from an interrupted run.
- `--model NAME`: optional Codex model; development default `gpt-5.6-luna`.
- `--effort low|medium|high|max`: requested effort; default `max`. Not a guarantee about actual provider reasoning/billing.
- `--timeout SECONDS`: positive timeout for the Codex process group, default 180. Failure does not produce a success JSON; existing diagnostics remain.
- `--language TEXT`: requested language of newly generated analysis, default `Korean`. Does not translate imported responses.

Frame budget, time range, resolution and deduplication belong to `extract`, not `analyze`. Current maximum is 24 samples per manifest. For longer or more detailed inspections, the calling AI can choose additional intervals and new manifests. IDs are local to each manifest, not global tracking IDs.

## Output contract: `shorts-analysis/1`

Preparation writes:

- `schema.json`: exact response shape, required fields, enums and frame IDs.
- `prompt.txt`: evidence and uncertainty instructions.
- `request.json`: individual images in chronological order, indices, sample positions and contract version. Contains local absolute paths; do not publish private requests/logs by accident.

Successful analysis/import additionally writes:

- `analysis.json`: `analysis` data plus `meta` provenance. Metadata includes backend, requested model/effort, provider-reported usage and runtime when available. Imports do not pretend to know the external model, usage or runtime.
- `report.md`: readable companion. JSON is the authoritative machine-readable result.

The Codex backend also leaves `response.raw.json`, `events.jsonl` and `stderr.log`. These can contain media-derived text and local diagnostics; they are not public examples. If a process is interrupted after a complete raw response is saved, use import with a new output directory to validate/recover it without calling the model again. An incomplete JSON response will be rejected.

### Per sampled frame

- `observation`, `composition`, `lighting_color`, `uncertainty`.
- `objects`: visible category, tentative correspondence hint, pose/state, estimated bounding box and confidence label.
- `text_regions`: readable text; subtitle/title/watermark/sign/other/uncertain category; estimated box; serif/sans/handwritten appearance; apparent weight; italic; color; outline; shadow; background; alignment; relative text height; confidence and uncertainty.
- `exact_font_name`: always null. A raster sample alone does not establish the exact font family, file or version. Report its appearance instead. No measured stroke thickness, font weight number or shadow-offset reconstruction is claimed.

Boxes use `[left, top, right, bottom]` in normalized 0–1 coordinates relative to the **individual supplied image**, not its contact-sheet cell. Null means unavailable/unreadable. These are VLM estimates, not calibrated computer-vision detections. `relative_height` is a visual estimate relative to image height, not a recovered font size. `track_hint` is a tentative cross-frame correspondence, not verified object identity.

### Across frames

- `temporal_observations`: referenced start/end frame, subject motion, camera motion, possible transition, uncertainty. Camera motion and subject action are kept separate.
- `editing_notes`: observed layout/editing characteristics, not inferred audio or guaranteed exact cut timing.
- `creation_suggestions`: explicitly proposed changes for making your own video, linked to supporting frame IDs. They are not proven explanations of engagement.
- `followup_ranges`: bounded intervals and reasons for closer inspection. The caller decides whether/how to use them with `extract --start/--end`; no automatic loop or cost is triggered.
- `limitations`: missing evidence, resolution/temporal gaps and other uncertainty.

Local validation checks the entire generated schema, finite numbers, boxes, complete/nonduplicate frame coverage, reference integrity and bounded follow-up intervals. **Passing schema validation does not prove the observations are factually correct.** Inspect source frames and use follow-ups when needed. Confidence labels are model judgments, not calibrated probabilities.

## Why individual images for detailed analysis?

The compact grid remains useful for a low-cost overview. Small grid cells can lose text and merge different moments visually. The analysis adapter instead consumes individual images from the same manifest so that frame identity and coordinates are explicit. This spends more visual input when necessary; it is **not** a new claim of lower token use or better accuracy in every case. Increase extraction width or narrow the interval for small text. No OCR engine, font database or pose-estimation model has been bundled.

IG-VLM directly motivates grid input. The thumbnail/detail idea is related to TS-LLaVA, and chronology checks are motivated by LLaVA-MLB, but their internal token/attention algorithms are **not implemented here**. See [RESEARCH.md](RESEARCH.md).

## Verification on 2026-09-10

A known-geometry, author-created 3-second fixture had a red rectangle at three discrete horizontal positions, a fixed `HELLO SHORTS` title, bold white sans-serif lettering, black stroke and a lower-right black shadow.

- A live `gpt-5.6-luna` run (requested effort `max`) transcribed the title in all three samples and reported its white/bold appearance, black outline and lower-right shadow.
- It detected rightward changes of the rectangle and approximately correct boxes at all three positions.
- It did **not** recover exact font/renderer settings. The shadow and outline overlap visually; descriptions are estimates.
- The sparse fixture only demonstrates position changes, not continuous gait or acceleration recognition. One model limitation statement over-generalized timestamp uncertainty; the prompt was subsequently clarified to distinguish known sample positions from exact decoded PTS. The initial live response is not a benchmark of that revised prompt.

A separate real 25.7-second vertical reference was analyzed as six individual images. All six had structured records; visible people/flowers/station scenery, watermark placement, blurred frames and the dark ending were covered. The source video has no verified subtitle ground truth, so it is not used as an OCR accuracy benchmark. Coarse samples still did not establish walking versus running. No third-party media or raw outputs are redistributed.

Subsequent focused-motion requests (8 frames over 7.5–10.5s, then 4 frames over 9–10.5s) timed out at 240s and 180s respectively without a model completion event. Their extraction completed (about 2.15s and 0.98s), but no analysis success file was written. No improvement in real walking/running classification was established. The cause of these delays is undetermined; reducing samples alone did not resolve them. A tiny text-only `low`-effort service check succeeded. The same four-image analysis with requested `low` effort subsequently completed in about **70.2s**, with provider-reported input 18,632/output 3,503 tokens (including harness context). This does not isolate the causal effect of effort or establish stable latency.

That completed run recorded all four frames, flower/person boxes and watermark styling, but screen/anatomical direction labels and camera-motion descriptions were not consistently reliable. It did not settle running versus walking. The prompt was then clarified to distinguish screen direction from anatomical laterality and not equate a centered subject with a fixed camera; this wording change has **not** been accuracy-benchmarked. No additional accuracy gain is claimed. The Codex adapter remains experimental; prepare/import are the provider-independent path.

The offline suite passed 97 tests after this extension. These are small smoke/behavior checks, not evidence of general accuracy, exhaustive recognition or production readiness. Tests use fake model processes for reproducible success/failure/timeout/schema checks; they do not measure model understanding.

### Generate your own known-source fixture

No font or video is bundled. Provide a locally installed, appropriately licensed bold sans-serif font:

```sh
.venv/bin/python examples/make_style_fixture.py --font /path/to/bold-sans.ttf \
  --out output/fixture
.venv/bin/python cli.py extract output/fixture/video.mp4 --out output/fixture-frames \
  --sampler uniform --max-frames 3 --width 360 --no-endpoint
```

`expected.json` records source geometry and renderer settings for evaluation, not input to the analyzing model. Compare its visible-text/box truth with the analysis yourself. Changing the font changes the test; keep the font fixed when comparing models.
